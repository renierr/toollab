Health Dashboard Storage model
ToolLab · lib/tools/health_dashboard

What gets stored, and when

A read-only collector for Android Health Connect. It imports measurements into typed SQLite tables built for fast queries over millions of rows — no JSON, no repeated text, and no surrogate keys on the dense tables. These tables are the tool's only storage.

01 Three shapes

Every Health Connect record collapses into one of three storage shapes. This distinction decides the table, the primary key, and how duplicates are handled — it is the single idea the whole schema rests on.

ShapeMeaningTablePrimary keyExamples
point A measurement at one instant. Series records explode into many. health_point (metric, t, v) heart rate, weight, SpO₂, speed sample
interval One value spanning a range. health_interval (metric, t0, t1, v) steps, distance, energy, hydration
session A container with a type, a title and child parts. health_session id, unique dedupe_key workout, sleep

The primary key is the measurement. health_point is keyed on (metric, t, v) and declared WITHOUT ROWID, so the row stores no identifier of its own. Two apps writing the same value at the same instant cannot produce two rows — which is how a Google Fit mirror of a direct writer collapses on insert, with no comparison pass at all.

Why not JSON

The previous model stored the Health Connect value verbatim as payload_json, so every aggregate ran json_extract over multi-megabyte blobs, and dense samples were written twice — once inside the blob and once as rows. Values are now converted exactly once, at the edge, into the unit the metric catalog declares.

05 The rollup that makes it fast

The dashboard never scans the dense tables. Every card, weekly chart and all-time total reads health_daily, one row per metric per day.

  • A decade of 26 metrics is roughly 95,000 rows — every read is a primary-key seek.
  • Refreshed only for the (metric, day) pairs an import actually touched, in the same transaction as the facts, so rollups can never disagree with them.
  • Keyed by local midnight as epoch millis, so a day always means the user's day. Every writer must produce the same instant dayKey() does: the full rebuild groups with strftime('%s', datetime(t, 'localtime', 'start of day'), 'utc') — dropping the trailing 'utc' yields the local wall clock read as UTC, which matches only where the offset is zero, and leaves rollups no reader ever finds.
  • Day bounds come from DateTime(y, m, d + 1), not + 24h — a fixed 24 hours lands an hour off across a DST change.
  • Each row describes one writer, the day's winner — see Duplicates. Aggregating across writers is what inflated step and distance totals.

Dense samples are read only for a drilldown — one workout's heart-rate curve — which is a bounded range seek on the (metric, t) key prefix.

Session summaries are joined, not carried. A workout's distance, energy and heart rate arrive from Health Connect as separate records, never as fields on the session. They are reduced into health_session's summary columns in SQL once both sides are stored, scoped to the imported window — so a workout list renders from one table.

07 Duplicates

Google Fit republishes other apps' data. A phone with both a direct writer and Google Fit sees most measurements twice — in captured data, 1,084,472 Google Fit heart-rate records alongside 390,830 from the watch's own writer.

Four mechanisms, in the order they apply:

  1. Don't read it. Switching a source off for a type becomes a dataOrigins filter on the read request, so Health Connect never hands over that writer's rows. Filtering beats deduplicating.
    The filter only ever excludes. It is sent only when something is actually switched off; with everything enabled no filter is sent at all. Building it from discovery instead — treating a bounded probe as the complete list of writers — made a full import return nothing but the one app that had written most recently.
    The change sync has to do this itself. synchronize() accepts no dataOrigins, so it drops excluded writers' records after reading them. Without that step a deselected source came back on every tool open.
  2. Collide on insert. Identical value at an identical instant cannot produce two rows, given the primary key. This catches exact mirrors — measured at 2,701 identical step rows and 104 identical weight rows.
  3. One writer per metric per day. A health_daily row is computed from a single writer, chosen by health_app.prio, then by whoever has the most rows that day, then by the lowest id. Never from all writers at once.
  4. Priority decides session mirrors. A session another app already stored for the same kind, overlapping by at least 70% of the longer of the two, is a mirror; the better-ranked writer keeps the slot and ties keep the first writer. The ratio is taken against the longer side so a short walk logged inside a long run is not swallowed by it. Same-app sessions only collapse on an exact range — an app logging two overlapping activities means it. Bounded by (kind, t0), no vendor names involved.

Near-mirrors never collapse. A republisher's heart rate differs from the direct writer's by a mean of 1.13 bpm, so those rows are legitimately distinct values and both persist. The primary key cannot help here, and neither can a comparison pass — only deciding which writer a day is computed from removes the duplicate from an aggregate.

Why summing across writers was wrong

The rollups used to be SUM(v) over every writer for a metric and day. A republisher re-buckets the same walk into different intervals, so the rows are not byte-identical, the primary key cannot collapse them, and both landed in the day's total — which is what inflated steps and distance. Averages had the same problem more quietly, with n, lo and hi mixing two streams.

Per day, not globally. Choosing the winner for each day separately is what keeps a republisher useful. On a day no other writer covered, it wins by default and its data still shows up — which is the whole reason a republisher must never be excluded wholesale. In the captured data the tablet was a byte-exact copy for dense metrics (274,188/274,188 heart-rate rows) and still the only source of 104 weight rows.

Switching a source off keeps its rows

Disabling stops a writer being pulled and drops it out of every read and rollup, but the rows it already contributed stay, so switching it back on is instant and free. Reclaiming the disk is a separate, explicit action — and it has to VACUUM, because deleting rows alone does not shrink the file: SQLite frees the pages and reuses them for later inserts.

08 Incremental sync

Opening the tool fetches only what changed, using Health Connect's own change tracking via synchronize(dataTypes, syncToken). The token is persisted as JSON in tool settings alongside a scope string.

Why not a time window

  • A watch that uploads Tuesday's data on Thursday writes behind any watermark. A window either misses those rows or has to stay permanently wide.
  • A window cannot observe deletions at all. Data removed in Health Connect previously stayed in the database forever.

The three states it must handle

StateCauseResponse
baselineNo token yet. The first call returns no records by design; it only marks a starting point.Store the token, report it as a baseline — never as "nothing changed". History comes from the full import.
scope changeThe token is bound to its type list; enabling a type invalidates it.Compare the stored scope string, re-establish, and let the full importer fetch the new type's history.
expiryHealth Connect expires tokens after about 30 days, throwing InvalidArgumentException.Clear the token, then recover automatically: take a fresh baseline, clear history_done and the pinned range on the enabled types, and re-read a window slightly wider than the expiry. Not the restart import — that deletes first, and re-reading is idempotent because the measurement is the primary key. needsFullImport now only survives when the recovery itself fails.

Long runs keep the CPU awake. Every read is a platform call into another process, and a full history is minutes of them. Discovery, the full import, the change sync, the cleanup, both directions of the backup and the dashboard's own toolbar action each hold a BackgroundWorkLease for their duration — a partial (CPU) wake lock plus a foreground notification — so Doze or app standby cannot suspend the app halfway through and strand a type mid-range. A background isolate is not an option: the plugin's method channels are bound to the main isolate, so a spawned one cannot reach Health Connect at all.

Backend sync is covered too, but by AppState.syncWithBackend rather than by this tool, since the lease has to span every tool in the run. It is taken only when more than one delegate is syncing: a single-tool sync is the cheap fire-on-open kind and would otherwise flash a notification every time a tool is opened. The one tool heavy enough to need protection on its own is this one, and its toolbar action already holds a lease around the whole chain.

Deletions reach sessions and intervals, not points. Those carry the Health Connect record id in origin; deleting an interval also repairs the daily rows for the days it covered. Dense points deliberately carry no id — a 36-byte identifier on every one of three million samples would cost more than the whole layout saves — so a deleted sample is reconciled by re-importing its window instead.

The reset drops the old tables on first open. It is detected by the stored schema version being higher than the current one, because migrate() would otherwise skip straight past a ladder that restarted low. Import watermarks, sync cursors and the old per-type source preferences are deleted with it.

First run after the reset

  1. Scan available data - seconds. This step is mandatory, not optional: types and writers do not exist until discovery registers them, so before it runs the selection screens have nothing to show and an import would store nothing.
  2. Data types - check what is enabled, and per type which apps to pull from.
  3. Apps - order the writers. The topmost writer with data for a day owns that day's totals, so a direct writer belongs above a republisher.
  4. Import selected data - full history for the enabled types. This is the long one, and it asks for confirmation with the selected type count first.
  5. Afterwards Sync changes now, or sync on open, fetches only what moved.

Not yet verified

  • Nothing has run against a real Health Connect store - no discovery, import or change sync has executed on a device.
  • The reset has not been observed on a database that actually holds the old schema.
  • Import throughput over full history is unmeasured under the new writer.

Re-import from scratch clears the tables first. It calls clearImportedData(), which deletes every row of health_daily, health_session_part, health_session, health_point and health_interval in one transaction, and resets history_done, range_start, range_end and n on every type. Selection survives: types, discovered writers, the app switches and the priority order are all kept, so the re-read pulls exactly what is selected now. It does not VACUUM — the freed pages are reused by the rows coming straight back in.

health_chunk and the stored sync cursor go with the rows. This is a local rebuild, not a deletion: with an empty manifest the next sync run has nothing to push and pulls every server chunk back, the Health Connect re-read adds this device's share on top, and the following push ships the union. Nothing shrinks on the server at any point, which also makes this the cleanest repair for a device whose local state has drifted.
Clean up is not reversible. Switching a writer off keeps its rows precisely so switching it back on is free; clean-up is the explicit decision to give that up in exchange for the disk. Afterwards, re-admitting the writer needs a fresh import. A switched-off data type keeps its rows either way: reads filter by metric, not by Health Connect type, so that data is still on the dashboard and is not "unused".

It is local, and offers no remove-everywhere choice, because it only ever touches writers that are globally switched off — and a switched-off writer is not pulled from the backend either. There is no separate pull-exclusion list anywhere: the writer switch is the filter, the same one that already decides what is imported and what is counted.

Why the per-app Health Connect screen cannot be opened

android.health.connect.action.MANAGE_HEALTH_PERMISSIONS with EXTRA_PACKAGE_NAME is the obvious deep link, and it does resolve — to com.google.android.healthconnect.controller's SettingsActivity. Starting it throws, because that activity is guarded by the signature permission GRANT_RUNTIME_PERMISSIONS: 

SecurityException: Permission Denial: starting Intent
  { act=android.health.connect.action.MANAGE_HEALTH_PERMISSIONS ...
    cmp=com.google.android.healthconnect.controller/...SettingsActivity }
  requires android.permission.GRANT_RUNTIME_PERMISSIONS

It is the link the system's own settings use, and no ordinary app can hold that permission. On the same device none of androidx.health.ACTION_HEALTH_CONNECT_SETTINGS, android.health.connect.action.HEALTH_CONNECT_SETTINGS or android.settings.HEALTH_CONNECT_SETTINGS resolves at all, so the cascade ends at Health Connect's launcher entry, and then at app info — which the UI now says out loud rather than leaving the user on an unexpected screen.

Granting is a different mechanism. Read access is granted through the permission request sheet, which the plugin raises from HealthConnectImporter.requestAccess(). Every entry that reads Health Connect calls it first and, when nothing comes back granted, offers this screen instead of reporting a successful import of zero records.

Why a switched-off app could still be imported

The full importer passes the allowed writers as a dataOrigins filter, which Health Connect only understands as an allowlist. The list can only be built from the writers discovery attributed to a type, and discovery is a bounded probe — so the filter is deliberately sent empty, meaning "no restriction", whenever every known writer for that type is allowed. Treating the probe as the complete writer list instead made a full import return almost nothing.

The consequence: a writer switched off globally that discovery never saw under a given type is not in that type's list, the filter goes empty, and Health Connect hands its records over anyway. They were invisible on the dashboard — every read and the rollups exclude a disabled writer — but they were stored. The importer now also drops excluded packages as the records arrive, which is what the change sync always had to do, since synchronize() takes no origin filter at all.

12 The numbers on the overview

Every card on the dashboard is one number, and the same label can mean three very different things: the newest reading, a day total, or a window sum. This section says which is which, where each one is read from, and what the metric page behind it shows.

Overview cards

"Latest" cards are a single stored reading — the newest row for that metric, a primary-key seek, never an average and never smoothed. HRV on the overview is therefore the last RMSSD value that was written, typically one morning reading, not a mean over the week; the seven-day mean only appears inside its detail page. All-time and window cards are the opposite: they never touch a reading, they read health_daily (or the session summary columns) so the cost does not grow with history.

The stage chart

Below is the real chart, drawn from the same layout constants and the same curve maths as health_session_timeline.dart, on a synthetic night. Toggle the curves in the legend and move the pointer across it.

Three things are worth reading off it. The bar is the night in order, so the cycles are visible as a shape. The four lanes under it answer "when was I in deep sleep" without hunting for a colour in the bar. And the curves sit above the bar rather than on it, because a line crossing coloured blocks is unreadable at phone width.

Why a lane is three bands, not one number. A curve's lane is a range label (15 px), the curve itself (40 px) and then clear space (14 px). The trailing gap is load-bearing: without it a curve's zero line falls exactly on the stage bar's top edge, and the line reads as glued to the bar however tall the lane is made. The height of the whole widget follows from the number of switched-on curves, so the chart never reserves space for a curve nobody asked for.

One lane, one scale

The four overlays share no range — 50 bpm, 14 rpm, 96 % and 60 ms on one axis would flatten everything but the widest. So each curve is scaled to its own minimum and maximum inside the session, which makes the shape readable and the absolute value meaningless; that is why the label prints the range it was scaled against, why the tooltip gives the nearest actual sample rather than a position on a line, and why every curve with data gets its own stats card further down the page — average, min, max and sample count for the night, not for the week. The cards follow the data, not the legend: switching a curve off hides the line, not the numbers behind it. They carry the curve's colour instead of green-low/amber-high: a low heart rate is good and a low oxygen saturation is not, so the arrows are left to mean direction only.

Scoring a night

health_sleep_quality.dart starts at 100 and subtracts for each of five checks that falls outside a standard adult reference range. No weighting, no model, nothing learned — five independent deductions and a floor at zero. Time asleep comes from the staged spans minus the awake ones when stages exist, from the source's own asleepMinutes when they do not, and from the whole span as a last resort.

Two results that surprise people, both deliberate. More deep sleep than the reference range costs 5 points — the range is two-sided, and an unusually deep night is as much an outlier as a shallow one. And the number of awakenings is counted and shown but never scored; only the minutes awake are. So a 6 h night with three brief wakes, 13 % deep and 24 % REM loses 10 points for duration alone and lands on 90 · Good. Note how close two of those sit to a cliff: 5 minutes less sleep would cost 25 instead of 10, and 12.9 % deep would cost another 10.

14 Generated test data debug builds only

An emulator holds no health data, which makes most of this dashboard impossible to look at. The generator is the one screen here that writes into Health Connect: a synthetic history over a chosen range, removable again on its own. The entry sits at the bottom of the Health Connect settings screen behind kDebugMode, so a release build never carries it.

The loop

Writing needs the permission declared, not just granted. An undeclared WRITE_* makes requestPermissions throw PERMISSION_NOT_DECLARED rather than come back denied. The eighteen the generator needs beyond the treadmill publisher's six sit in android/app/src/debug/AndroidManifest.xml, so they merge into debug builds alone and a release never asks for write access to weight, sleep or blood pressure. Keep that list in step with HealthDebugSeeder._typesByGroup — and note that a manifest change needs a full rebuild, not a hot reload.
Why step 03 exists. The full importer sends the allowed writers as a dataOrigins allowlist, and that list can only name writers discovery has attributed to a type. On a device that already discovered other writers, a brand-new one is missing from the list until the probe runs again. On an empty emulator the filter is empty — "no restriction" — and the import finds it either way.

Every record is stamped, and that is what makes it removable

The wipe reads the generator's types back, keeps the records carrying this and deletes them by id. Real data — treadmill workouts above all — is never matched. A time-range delete could not tell the two apart.
Epoch day
Derived from the day, not from the run. Generating the same day twice replaces its records instead of adding a copy, so feed → clear → feed converges on the same history.
Its own source
Android attributes every record to the writing package, and this app has one — so generated rows would be labelled and deleted as the treadmill publisher's real workouts. HealthConnectMapper.packageOf files anything carrying the prefix under de.renier.tool_lab.generated instead, which gives it its own row in Apps, its own switch and its own priority.
Part
Fixed per record within a day. Renaming one orphans everything already written under the old name, exactly as in the treadmill publisher.

The night's curves live with the sleep group, not with vitals. The sleep screen lays oxygen, breathing and HRV over the session, and a morning spot reading falls outside it — so generating every vital in the list still left those overlays empty. They are sampled inside the night and owned by the group that owns the night, which makes picking sleep alone yield a complete one. vitals keeps its own daytime readings of the same metrics; the two coexist, as they would on a real device.

A preset is nothing but a set of groups, so a preset and a hand-picked selection are the same thing to the generator: Everyday is activity + heart + sleep + body, Athlete adds workouts and hydration, Clinical is heart + body + vitals, and Everything is all seven. Ranges run from 7 days to a year.

Two limits worth knowing. BodyMassIndexRecord is never written — Health Connect has no such record type, whatever the plugin's type list suggests. And a batch Health Connect rejects is retried one record at a time, so a type this platform version will not take costs one record rather than the two hundred it shared a write with.

Removing also drops the generating package's rows through deleteAppData. Deleting in Health Connect alone would leave everything already imported sitting in the typed tables — health_point carries no record id, so the change sync cannot retract those rows on its own.
